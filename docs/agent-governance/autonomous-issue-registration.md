# Autonomous Issue Registration

이 문서는 Seorilabs 제품 저장소에서 근거 있는 개선 일감 하나를 찾아 GitHub 이슈로 등록하는 조직 공통 계약이다. 로컬 스킬이 없는 클라우드 환경에서도 이 문서와 [`autonomous-issue-policy.yaml`](../../contracts/autonomous-issue-policy.yaml), 대상 저장소의 문서만으로 동일한 이슈를 작성할 수 있어야 한다.

## 읽기 순서와 변경 경계

1. `contracts/autonomous-issue-policy.yaml`
2. 이 문서
3. 대상 저장소의 `AGENTS.md`, `.seorilabs/app.yaml`, README와 제품·분석 문서
4. 현재 코드, 열린·최근 닫힌 이슈와 PR, 사용 가능한 지표·공식 자료
5. 로컬 환경에 관련 스킬이 있으면 증거 수집 어댑터로 사용

기계 판독 계약과 문서가 충돌하면 계약이 우선한다. 이 루틴은 이슈 등록까지만 수행한다. 코드, 브랜치, PR, 배포, 콘솔 설정, 프로덕션 리소스를 변경하지 않는다.

## 한 실행 한 이슈

- 한 실행에서 새 이슈를 최대 한 개만 만든다. 유효한 후보가 없으면 `신규 이슈 없음`으로 끝낸다.
- `registration=EXCLUDED`는 가장 앞선 차단 gate다. 저장소 clone, 지표 조회, 리서치와 GitHub mutation을 모두 하지 않는다.
- `registration=DISABLED`이거나 정책에 없는 저장소도 동일하게 건너뛴다. 신규 저장소를 제품이라고 추측해 자동 편입하지 않는다.
- `registration=ENABLED` 저장소만 정책에 적힌 순서로 순회한다. KST 기준 연중 일수의 0 기반 값을 ENABLED 저장소 수로 나눈 나머지를 시작 위치로 사용하고, 목록 끝에서는 처음으로 돌아온다. 한 번만 순회하고 이슈 하나를 만들면 즉시 종료한다.

## 저장소별 사전 gate

비용이 드는 분석 전에 다음을 순서대로 확인한다.

1. 열린 `autopilot` 이슈 수가 정책의 `openAutopilotIssueLimit` 이상이면 건너뛴다.
2. 열린 이슈와 최근 닫힌 이슈, 이를 닫는 PR의 `closingIssuesReferences`를 확인한다. 같은 문제·인수조건이면 중복 후보로 폐기한다.
3. 최근 수정이나 배포 뒤 효과를 관찰할 시간이 충분하지 않으면 post-fix gate로 건너뛴다.
4. 표본이 작거나 데이터가 불완전해 행동 변경을 뒷받침하지 못하면 행동 변경 이슈를 만들지 않는다.
5. 저장소 변경만으로 닫을 수 없고 기획·스토어·법무·계정·배포 승인이 필요한 후보는 자동 처리 이슈로 만들지 않는다.

사전 gate 결과는 실행 보고에 저장소별로 남긴다. 제외와 no-op은 실패가 아니다.

## 근거 수집과 후보 판정

사용 가능한 근거를 다음 순서로 사용한다.

1. GA4 BigQuery export, AppsInToss 콘솔, 스토어 별점 추이 같은 실제 제품 지표
2. 현재 기본 브랜치의 코드·테스트·계측 계약과 명확한 결함
3. 공식 문서와 출처가 확인되는 온라인 리서치

- 라이브 수치를 코드에서 추론하지 않는다.
- 행동 변경 후보에는 측정 기간, baseline, 표본 한계, 코드 위치 또는 공식 출처 중 검증 가능한 근거가 있어야 한다.
- 가설을 측정할 이벤트·파라미터가 없으면 행동 변경 대신 `instrumentation` 이슈로 전환한다.
- 신규 콘텐츠, 일반 밸런스, 경제 확장처럼 제품 결정을 대신하는 후보는 등록하지 않는다.
- 인수조건은 대상 저장소에서 구현하고 자동 또는 명시된 수동 절차로 검증할 수 있어야 한다.

## 제목 계약

제목은 고객이 겪는 문제와 해결 뒤 달라지는 가치를 짧은 한국어 평문으로 쓴다.

- 좋은 예: `재접속하면 사라지는 튜토리얼 진행을 이어서 할 수 있게 한다`
- 좋은 예: `광고 실패 뒤 멈추는 보상 흐름을 다시 진행할 수 있게 한다`
- 금지: `[P1]`, `[BUG]`, `[repo]`, `seorilabs/foo:` 같은 말머리
- 금지: `P1:`, `U1`, `N1` 또는 같은 형태의 에이전트 처리 순서 코드

중요도, 유형, 근거와 실행 환경은 제목이 아니라 라벨로 표현한다. 저장소명은 실제 고객 문제를 설명하는 데 필요한 고유명사가 아닌 한 제목 앞에 붙이지 않는다.

## 라벨 계약

새 이슈에는 다음 라벨을 모두 붙인다.

- `autopilot`
- `P1`~`P4` 중 정확히 하나
- `autopilot:local` 또는 `autopilot:cloud` 중 정확히 하나
- 필요할 때 `bug`, `enhancement`, `instrumentation`
- 근거에 맞는 `evidence:ga4`, `evidence:console`, `evidence:store`, `evidence:research`, `evidence:csv`

`no-autopilot`, `blocked`, `approval:*`가 필요한 일은 자동 등록 후보가 아니다. 우선순위는 사용자 영향, 재현 범위, 데이터 악화 정도와 구현 위험을 근거로 P1~P4 중 하나를 선택한다. 우선순위나 작업 순서를 별도 제목 코드로 만들지 않는다.

## 실행 환경 판정

라벨은 이슈를 발견한 환경이 아니라 구현과 검증에 필요한 환경으로 결정한다.

### `autopilot:cloud`

다음 자료만으로 구현·검증을 끝낼 수 있을 때 사용한다.

- 대상 GitHub 저장소와 조직 계약
- 저장소 문서, 이슈와 PR
- 공개 공식 문서
- 저장소 CI

본문의 실행 환경 절에 `로컬 전용 의존성 없음`을 명시한다.

### `autopilot:local`

다음 중 하나라도 필요하거나 판단이 불명확하면 사용한다.

- 로컬 스킬 또는 로컬 전용 데이터·자산
- `~/.config/seorilabs` 자격증명 카탈로그
- BigQuery, GCP, Kubernetes 또는 비공개 Backoffice 데이터
- 로그인된 브라우저·콘솔
- 실기기·에뮬레이터
- Obsidian 문서

본문의 실행 환경 절에 필요한 스킬 이름, 리소스와 검증 방법을 구체적으로 적는다. 비밀값은 적지 않는다.

## 이슈 본문

다음 절을 빠짐없이 작성한다.

```markdown
## 고객 가치

## 문제와 근거

## 해결 후 기대 상태

## 범위
포함:
-

제외:
-

## 인수조건
- [ ]

## 검증 방법

## 실행 환경
- 분류: autopilot:local 또는 autopilot:cloud
- 필요한 스킬·리소스: 없음 또는 구체적인 이름
```

지표 근거이면 측정 기간, source, baseline과 표본 한계를 `문제와 근거`에 포함한다. 파일 경로와 함수가 확인되면 현재 기본 브랜치 기준 위치를 적는다.

## 등록 직전 확인

1. 제목 금지 패턴과 `U숫자`·`N숫자` 코드를 검사한다.
2. 필수 라벨, 실행 라벨 하나, 우선순위 라벨 하나를 검사한다.
3. 본문 필수 절과 실행 환경 근거를 검사한다.
4. 중복 이슈와 닫는 PR을 다시 읽는다.
5. 모든 gate가 통과한 후보 하나만 등록하고 즉시 종료한다.
