# 실제 SDK 개발 검수를 플랫폼 검수 근거로 인정

- 상태: 승인 범위 구현. 2026-10-18 사용자가 도마뱀 출시 대화의 변경안에 **"정식 변경·1.8.4 진행 승인"**으로 답했다. 승인은 16개 일괄 실기기 요구의 개발 검수 대체, 중앙 규칙·검증기 정합화, 앱의 두 계획 개정과 새 패치 후보 공개 진행이다. 기기 사용은 포함하지 않는다.
- 기준: `.github` `a2da27879d58da7f6e018be530162cb20e6273a1`.
- 변경 대상: 계획·실행 schema, 승인 계획 합성, before-release 플랫폼 하한 충족 판정과 문서. 태그·업로드·서명·production 승격 권한은 바꾸지 않는다.

## 목적과 사용자 흐름

개발 환경으로 검증 가능한 기능을 실기기에서 다시 실행하도록 강제하는 대신, 실제 네이티브 SDK가 동작하는 개발 환경의 근거를 기능·마켓별로 승인받아 쓴다. 일반 headless·단위 검사로 SDK 연결을 대체하지 않는다. 첫 플랫폼 기능도 검수를 생략하지 않고 승인된 실제 SDK 실행으로 확인한다.

설계 승인 → 개발 회귀 → 같은 후보의 네이티브 테스트 빌드 → 승인된 실제 SDK 개발 검수 또는 필요한 기기 검수 → before-release → 기존 마켓 절차 순서다. 기기 조회·실행은 별도의 필요성 소명과 명시적 승인을 따르며 이 계약이 사용 허가를 발급하지 않는다.

## 데이터와 책임

기능 목록 v2의 승인 `test-plan.json`에 선택 배열 `platformValidation`을 추가한다. 각 항목은 `featureId`, `target`, `kind: "native-development"`, `reason`, `checks`를 가진다. `checks`는 실행 기록에서 통과해야 할 시나리오 ID다. 기능에 platformPaths가 있어야 하며, 해당 마켓과 dev 환경이 그 계획에 있어야 한다. 기능·마켓 조합은 중복할 수 없다.

여러 설계가 한 후보에 결속되면 **모든 계획**이 같은 기능·마켓의 대체 환경을 승인해야 하며 요구 시나리오는 합집합이다. 승인 커밋·후보 조상 검사는 기존대로 유지한다. 일반 `floorOverrides`는 새 플랫폼 기능을 면제하지 못한다.

`native-development` 실행에만 선택 `nativeSdk`를 허용한다. 이 객체에는 다음이 모두 필요하다.

- `mode: "real"`, `runtime: "ios-simulator" | "android-emulator"`, `sdkNames`.
- `artifact: {path, sha256}`와 검수용 파생 빌드의 차이를 밝히는 `limitations`.
- 실행의 `target`, `build`, `configurationFingerprint`. `sourceSha`, 독립 실행자·시간·격리 데이터·passed 시나리오는 기존 필수 조건이다.

스키마와 검증기는 이 선언의 구조·대상·일관성을 검사한다. SDK 실행 사실과 산출물 해시의 원문 대조는 실행자와 교차 검수자가 확인한다. JSON 선언만으로 실제 실행을 증명할 수 있다는 주장을 하지 않는다. 기기 근거 역시 원문과 함께 검수한다.

## 판정과 실패

기존 platform/platform-first 하한 계산은 그대로다. before-release에서 대상 마켓의 물리 기기 실행, 또는 모든 결속 계획에 승인된 실제 SDK 개발 실행이 하한을 채운다. 개발 실행은 런타임 플랫폼이 마켓에 맞고, 하나의 유효한 실행 안에 요구 시나리오와 기능 ID가 모두 있어야 한다.

다른 마켓·플랫폼, 다른 SHA·설정 지문, 만료·시간 역전, 작성자 실행, fake SDK, 산출물 해시 누락, 필수 시나리오 누락은 거부한다. 현재 CI API 검증은 headless workflow만 확인하므로 nativeSdk 실행의 executor=ci는 허용하지 않는다. 필요한 실제 기기 인증·하드웨어 검수는 개발 대체 항목에 넣지 않는다. 기존 계획에 명시된 android/ios 실행 환경은 이 기능으로 대체되지 않는다.

## 인수조건과 검증

1. 기존 계획·기존 실행은 동일하게 판정하고, 대체 승인 없는 첫 플랫폼 기능 하한을 유지한다.
2. 기능·마켓·실제 SDK·필수 시나리오·독립성·유효기간이 맞는 실행만 플랫폼 하한으로 인정한다.
3. 여러 계획 중 하나의 승인 누락과 모든 부정 입력을 거부한다.
4. 다른 마켓의 물리 기기 실행도 대상 마켓 하한을 채우지 못한다.

`tests/native-development-validation.test.mjs`에 먼저 실패를 확인한 뒤 구현한다. 기존 테스트 등급·headless·CLI·통합 검사를 포함한 `npm test`로 회귀를 확인하고 릴리스 검증 로직 변경이므로 로컬 Claude 읽기 전용 교차 리뷰를 요청한다. 정책 변경에는 제품 화면·데이터 마이그레이션·UI 재설계가 없다.

## 적용과 복구

선택 필드가 없는 기존 계획은 기존 하한을 그대로 쓴다. 앱 계획을 바꿀 때 새 승인 커밋을 후보의 조상으로 포함하고 새 후보에서 다시 실행한다. 기존 태그의 계획이나 실행 결과를 덮어쓰지 않는다. 문제가 생기면 새 계획에서 대체 항목을 제거해 기존 물리 기기 하한으로 복귀하거나 중앙 변경을 별도 PR로 되돌린다. 미실행을 통과로 기록하거나 검증기를 생략하는 복구는 없다.
