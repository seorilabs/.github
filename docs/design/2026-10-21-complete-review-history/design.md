# 이전 후보의 완전한 검수 기록 보존

사용자가 [Play 연령 정보 보완 설계](https://github.com/seoleeapps/starlit-apprentice/blob/3383abd89133b4abb37ad2c2af3551b1c926b9b5/docs/design/2026-10-21-play-age-signals/design.md)와 같은 커밋의 테스트 계획에 “승인”이라고 답했다. 승인 관측을 기록한 시각은 2026-10-21T12:23:30Z다. 원래 응답 발신 시각을 추정한 값이 아니다. 승인 범위에는 이전 후보의 실제 UI4를 보존하고 새 후보의 UI5~7 세 회차를 요구하는 중앙 기록 양식 보완이 포함된다. 기기, IAM, 제품 SDK와 마켓 작업은 이 중앙 변경에서 실행하지 않는다.

## 문제와 동작

17005d45의 복구 계약은 최초 세 회차의 결손을 사실대로 보존하지만, 그 뒤 모든 회차에 현재 후보 SHA를 요구한다. 실제 UI4를 완료한 뒤 새로운 플랫폼 요건으로 후보를 바꿔야 할 때, 과거 UI4를 보존하고 새 후보의 5~7회를 기록할 수 없다. 이미 실행한 UI4를 취소하거나 번호와 SHA를 바꿔서는 안 된다.

`reviewHistoryRecovery.completedRounds`를 선택 배열로 추가한다. 각 항목은 원래 `round` 전체, 당시 `implementer`, `originalReportSha256`과 원본 `evidence`를 보존한다. 이 완전한 과거 기록의 SHA와 계획 및 실행 시각은 null을 허용하지 않는다. 최초 결손 1~3회와 구분하며 모두 새 후보의 합격 수에는 0회로 센다. 원본 해시는 기존과 같이 bytes 식별 선언이고 실행자가 실제 파일과 판정을 별도 대조한다.

전체 번호는 결손 이력 1~3회, 완전한 과거 기록 4회부터, 현재 후보의 새 회차 순으로 끊김 없이 이어야 한다. 과거 완전 회차도 실제 계획과 시작 및 완료 순서, 당시 구현자와 다른 검수자, 추가 회차 상한과 그 계획 이전에 존재한 사람 승인을 검사한다. 미래의 새 승인으로 과거 회차를 소급 승인할 수 없다. 당시 승인은 최초 세 회차 종료 이후여야 한다.

현재 후보의 새 회차는 여전히 최소 세 건이며 모두 같은 현재 SHA, 전체 기능의 기능과 UX, 독립 검수, 실행 전 계획과 168시간을 충족해야 한다. 새 회차를 덮는 추가 승인은 마지막 과거 회차 완료 후이면서 각 새 계획 이전이어야 한다. 과거 UI4의 예전 기능 목록에 나중에 추가한 기능을 요구하지 않는다. 과거 실패 판정은 보존하고 해결 근거가 필요하며 마지막 새 회차는 통과해야 한다. 기존 두 승인 시각과 상한은 `additionalIterationApprovals`로 각각 보존한다.

기존 정상 v2, 최초 세 회차만 보존하는 복구 입력과 v1의 동작은 유지한다. v1에는 새 필드를 허용하지 않는다. 원래 세 결손 회차의 갯수와 필수값은 바꾸지 않고, 검수 횟수나 플랫폼 및 출시 하한을 면제하지 않는다. 개별 앱 grant와 CLI 생략 옵션을 추가하지 않는다.

## 인수조건과 검증

- CH-01: 과거의 완전한 UI4와 원래 승인 상한 6을 그대로 보존하고 새 후보의 5~7회를 승인 상한 7로 검증한다. 이 입력의 현행 schema 거부를 먼저 재현한다.
- CH-02: 과거 4회차도 SHA, 시각, 원본 해시, 독립성, 실제 회차 번호와 당시 추가 승인이 필수다. 새 승인만 남기거나 늦은 승인을 소급 적용하면 차단한다.
- CH-03: 새 회차가 두 건뿐이거나 SHA, 전체 기능, 독립성, 시간 순서, 168시간과 추가 승인 상한을 어기면 차단한다. 과거 세 결손과 완전 기록은 합격 수에 넣지 않는다.
- CH-04: 기존 정상 입력과 복구 입력의 동작이 유지되고 전체 계약 테스트, package 검사, actionlint와 diff 검사가 통과한다.

변경은 서비스 계약의 L1 개발 검증이다. 기준 SHA를 명시하고 첫 출시 L3로 오판하지 않는다. 합성 fixture의 계약 테스트만 실행하며 앱 UI나 실기기 검수로 표시하지 않는다. 정상 PR, 로컬 MiniMax 리뷰와 필수 CI를 거쳐 반영하고, 사용하는 앱은 새 후보의 실제 세 회차를 완료한 뒤 원본 근거로 게이트를 실행한다.
