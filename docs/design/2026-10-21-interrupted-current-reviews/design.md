# 중단된 현재 후보 검수의 원본 보존

사용자는 제안 원문 SHA256 `7230f670c0a2ae7cd2e45441019a1942cec6c6e10c8aea2161117e0ccdf30749`에 “원장 보완과 11회차 1회 승인 (권장)”으로 답했다. 확인 시각은2026-10-21T15:47:02Z이며 발신 시각을 추정하지 않는다. 이 설계는 승인된 조직 공통 기록 보완만 구현한다. 관련 티켓은 #298, 기준 중앙 SHA는 `f73637d7855a726e083da76fde82a6499ed53972`다. 앱 실행, 기기와 마켓 작업은 이 PR에서 하지 않는다.

## 문제와 흐름

전체 범위를 실행하다 중단된 회차는 실제 실패와 미실행 범위를 보존해야 한다. 현재 양식은 모든 current 회차에 전체 기능 검수를 요구하므로, 두 완전 검수와 한 부분 실패 뒤 새 완전 검수를 추가할 때 부분 회차를 사실대로 남길 수 없다. 부분 실패의 기능 ID 선언을 실제 전체 검수로 취급하거나 공식 종료를 다시 쓰지 않는다.

기존 `reviewRounds`의 선택 `interruption`에 reason,originalReportSha256,evidence와 actualScope를 추가한다. actualScope의 completed,incomplete,notRun은 원본에서 식별되는 실행 단위 목록이다. 화면 크기와 언어가 다르면 서로 다른 단위 ID로 적고, 미완료 또는 미실행 단위가 적어도 하나 있어야 한다. 서로 다른 상태 목록에 같은 단위를 중복 기록하지 않는다. 원래 round의 SHA, 계획과 시작 및 완료 시각, 검수자와 실패 판정은 그대로 보존한다. 원본 bytes의 hash와 판정 및 실제 범위는 실행자가 별도 대조하며 검증기가 임의 URL의 진위를 보장하지 않는다.

중단 표시는 기능과 UX의 failed 또는 blocked에만 사용한다. 원래 functional/ux featureIds가 요구 범위를 나타낸 경우 이 표시가 실제 범위 결손을 명시하며 그것을 검수 완료로 세지 않는다. 같은 후보의 완전한 독립 검수 수에는0회, 실제 순서와 승인 상한에는1회로 센다. 예를 들어 전체 순번이8,9,10,11이고10만 중단됐으면8,9,11 세 회차의 실제 전체 검수가 필요하다.10은 원래 실패이며11의 실제 재검수 해결 근거를 연결해야 한다. 마지막 회차는 중단일 수 없고 기능과 UX가 모두 통과해야 한다.

이 경로를 쓰면 현재 회차 모두에 같은 SHA,168시간과 독립성 및 사전 계획을 검사하고, 중단되지 않은 모든 회차는 전체 기능을 검수해야 한다. 중단 회차도 원래 번호와 시각 순서, 사람 사전 승인 및 실제 상한, 실패 해결을 검사한다. 기존 최초3회 결손과 완전 과거 기록은 계속0회이며 `completedRounds`에 중단 회차를 넣지 않는다. 기존 정상 v2와 v1 입력은 바꾸지 않고 v1에는 필드를 허용하지 않는다. 플랫폼과 공개 하한, 실행 근거 요구를 낮추지 않으며 앱 전용 grant와 생략 옵션을 추가하지 않는다. 제품 UI 변경이 없어 화면 예시는 해당 없다.

## 인수조건과 검증

- IR-01: 중단의 원본 hash,실제 완료/미완료/미실행 범위와 원래 실패 및 시각을 요구하고 통과 판정을 중단으로 위장하지 못한다.
- IR-02: 중단을0회로 세면서 완전한 현재 후보 검수 최소3회와 마지막 통과를 요구한다. 중단만 더하거나 과거 회차를 전용해 최소 수를 채우지 못한다.
- IR-03: 같은 SHA,전체 기능,168시간,독립성과 사전 계획,연속 순서,실제 번호 상한과 원래 사전 승인,실패 해결 및 플랫폼 하한을 유지한다.
- IR-04: 기존 정상 v2와 두 이력 복구 및 v1의 동작이 유지되고 전체 계약 테스트,package 검사,actionlint와 diff 검사를 통과한다.

L1 dev에서 합성 fixture의 요구사항 red를 먼저 확인하고 schema,검증기,정본 문서를 최소 수정한 뒤 회귀를 검증한다. 기준 SHA를 명시해 첫 출시 L3로 오판하지 않는다. PR 전 독립 diff 점검과 로컬 MiniMax 리뷰, Ready PR의 필수 CI 후 squash로 반영한다. 앱의 실제 새 검수는 정식 반영 뒤 별도 계획과 실제 결과가 있을 때만 근거로 사용한다. 이 변경 자체를 앱 검수 통과로 표시하지 않는다.
