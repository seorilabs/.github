# 개발 워크플로우 개정 설계안

[시각화로 설계 검토하기](visuals/workflow.html)

현재 개발 흐름에 구현 전 사람의 설계 검토, 테스트 우선 작성, UI 앱의 3회 기능·UX 검수, 빌드와 배포 직전 개발 실행 환경 E2E를 추가한다. `/plan`은 에이전트가 전체 작업을 정리하는 단계다. 설계 승인, PR 병합, 출시 승인은 서로 다른 결정으로 기록한다.

이 문서는 2026-10-08 사람이 승인한 설계의 정본이다. 정책·템플릿·스킬과 중앙 검증 경로는 이 PR에서 반영한다. 예약 작업 활성화, 앱별 Wiki 게시와 제품 출시를 승인한 것으로 해석하지 않는다. 사용자가 선택한 대로 문서 정본은 `docs/design`, Wiki는 목록·요약·티켓 링크, 검수는 작성자와 다른 리뷰 에이전트가 담당하는 방식으로 확정했다. 승인 근거: 사용자의 “반영하자. 진행하면서 이치에 안 맞거나 stale한 것들은 지우고 버리고 병합하는 것도 잊지 말자.” 승인 대상 v1 원문 SHA-256은 `c4f6a30c0ef316c1a4aaae7c54e0bb582b2e20936076dc8a33d62975d9b4ad34`, 시각화는 `042f91f60faafd0d366d74ec0ff11325ac231786c4a55e9703214ea4e2f97dbc`이다.

## 1. 단계와 산출물

| 단계 | 책임 | 하는 일 | 다음 단계로 넘어가는 근거 |
|---|---|---|---|
| `/plan` | 작업 에이전트 | 전체 할 일, 순서·의존성, 영향 레포, 미확정 사항, 필요한 승인·자원 정리 | 작업 목록·범위·우선순위·설계할 작업 구분 |
| 작업별 설계 | 작업 에이전트 | 실제 구현할 작업의 흐름·구조·데이터·실패 동작·인수조건·테스트 계획 작성 | 검토 가능한 설계 문서와 시각 자료 |
| 사람의 설계 검토 | 사용자 | 제품 동작·기술 선택·범위·인수조건·검수 계획 검토 | 정확한 설계 버전 또는 커밋에 대한 승인 기록 |
| 실행 티켓 연결 | 작업 에이전트 | 승인 설계를 기반으로 대상 레포에 구현 티켓 발행·연결 | 티켓 ↔ 설계 원본·승인 버전 ↔ Wiki 목록 |
| 테스트 우선 구현 | 작업 에이전트 | 실패하는 행동 테스트 → 통과시키는 최소 구현 → 관련 회귀 검증 | 요구사항에 해당하는 실패·통과 실행 결과 |
| UI 앱 3회 검수 | 구현자와 검수자 | 매 회차 계획 → Editor에서 기능·UX 실행 검수 → 수정·재확인·기록 | 3개 회차 기록과 전체 통과 조건 |
| PR·CI·병합 | 작업 에이전트 | Ready PR, 필요한 Copilot 리뷰, 필수 CI, thread 해결, 충돌 확인 | 현재 HEAD 기준 통과와 원격 merge readback |
| 최종 Editor E2E | 작업 에이전트·검수자 | 빌드 직전 및 배포 직전에 이번 변경과 기존 구현 기능 전체를 연결해 실행 | 정확한 후보 소스·설정·테스트 환경의 E2E 보고서 |
| 빌드·배포·공개 확인 | 승인받은 실행자 | 승인한 태그·마켓·제출 범위 안에서 실행하고 각 단계 재조회 | 산출물·기기 QA·마켓·공개·실제 실행 각각의 증거 |

설계 승인 뒤 범위, 사용자 동작, 데이터 규약, 주요 구조 또는 인수조건이 실질적으로 달라지면 설계를 수정하고 해당 변경에 대한 사람 검토를 다시 받는다. 같은 승인 버전과 범위에 대해 승인을 반복 요청하지 않는다. 기존 접수 이슈가 충분한 실행 티켓이면 중복 이슈를 만들지 않고 설계·승인 링크를 보강한다.

## 2. 설계서 필수 요소

문서 크기는 변경 규모에 맞춘다. 작은 수정은 한 페이지로 작성할 수 있지만 아래 항목의 판단은 남긴다. 해당 없는 내용은 `해당 없음`과 이유를 적는다. 빈 항목이나 미확정 제품 결정은 승인 완료로 표시하지 않는다.

| 필수 요소 | 남겨야 하는 내용 | 우선 사용할 시각 자료 |
|---|---|---|
| 목적·범위·근거 | 해결할 사용자 문제, 기대 결과, 포함·제외, 기존 동작과 확인 근거, 제약 | 변경 전후 예시·범위 표 |
| 사용자 흐름·화면 상태 | 시작→핵심 행동→완료, 탐색, 빈 상태·로딩·오류·취소·복구·접근성 | 화면 흐름·와이어프레임·상태도 |
| 구조·책임·의존성 | 바뀌는 모듈, 책임·경계, 연결 서비스, 기존 패턴 재사용 | 구성도·데이터 흐름 |
| 데이터·인터페이스·실패 처리 | 입력·출력·계약, 저장·수명, 호환·이관, 타임아웃·중복·재시도·권한 실패 | 관계도·시퀀스·실패 경로 |
| 품질 요구사항 | 응답·성능 목표, 보안·개인정보, 접근성, 작은 화면·큰 글자 등 적용 조건 | 측정 조건·목표 표 |
| 대안·주요 결정 | 검토한 대안, 선택 이유, 영향과 확인할 가정 | 대안 비교 표·결정 기록 |
| 인수조건·테스트·검수 | 관찰 가능한 완료 기준, 조건별 테스트, 데이터·환경·방법·예상 결과, 3회 UI 검수 및 최종 E2E 계획 | 조건→테스트→증거 연결 표 |
| 적용·운영·되돌리기 | 작업 순서·의존성, 릴리스 영향, 계측, 오류 대응·롤백, 남은 위험·담당자 | 적용 순서·복구 흐름 |
| 승인·추적 | 설계 식별자·버전, 승인자·시각·근거, 티켓·PR·테스트 보고서·대체 설계 링크 | 상태·링크 표 |

장문 설명으로 그림을 대신하지 않는다. 기본은 사용자 또는 실행 흐름 그림과 바뀌는 구조 그림, 인수조건·테스트 연결 표다. 데이터·상태·연동 변경이 없으면 불필요한 그림을 만들지 않고 그 이유를 적는다. 핵심 화면 변경은 실제 예시 또는 시안을 함께 검토한다. 제품 UI의 시각 방향 선택은 기존 `game-ui-design`·앱 디자인 정책과 함께 적용한다.

필수 요소 선정은 [arc42의 목적·제약·구조·동작·결정·품질·위험 항목](https://arc42.org/overview/)과 [필요한 수준만 선택하는 C4 다이어그램](https://c4model.com/diagrams)을 참고했다. 위 표는 조직 운영에 맞춘 제안이며 특정 표준 준수를 주장하지 않는다.

## 3. 인수조건과 테스트 계획의 연결

조건마다 식별자를 부여해 설계, 티켓, 테스트, PR, 검수 기록에서 동일하게 사용한다.

| 조건 | 관찰할 동작 | 테스트 방법·환경 | 테스트 데이터·시작 상태 | 통과 기준 | 남길 증거 |
|---|---|---|---|---|---|
| 조건 1 | 사용자가 핵심 행동을 완료 | 도메인 테스트 + 개발 실행 환경 E2E | 격리된 새 상태 | 설계한 결과와 저장 상태 일치 | 실패·통과 로그 + 실행 기록 |
| 조건 2 | 실패 뒤 안내와 복구 | 실패 입력·네트워크 오류 재현 | 별도 테스트 계정·실패 조건 | 진행 상태 보존, 복구 행동 가능 | 오류 로그·재현 단계·화면 |
| 조건 3 | 기존 기능 유지 | 핵심 기능 목록을 끝까지 실행 | 기존 형식의 격리 저장 | 결과·데이터 손상 없음 | 회귀 결과·최종 E2E 보고서 |

위 내용은 형식 예시이며 어떤 제품을 실제 검증한 결과도 아니다. 실제 설계에서는 예상 결과와 측정 조건을 구체적으로 바꿔 쓴다.

테스트 계획에는 자동화 가능 여부, 사용 명령 또는 재현 단계, 환경·의존 서비스, 격리 데이터, 예상 결과, 기능·UX 검수자, 확인할 증거를 적는다. 미실행·차단은 통과와 구분한다.

## 4. 테스트 우선 구현

1. 승인 설계의 인수조건 하나를 선택한다.
2. 아직 충족하지 않은 동작을 검증하는 테스트를 먼저 작성한다.
3. 구현 부재 또는 기존 결함 때문에 그 테스트가 실패하는지 확인한다. 잘못된 테스트 문법·환경 오류를 요구사항의 실패 증거로 대신하지 않는다.
4. 테스트를 통과시키는 최소 구현을 작성한다.
5. 해당 인수조건과 관련 회귀 테스트를 실행하고 결과를 기록한다.
6. 설계와 테스트가 승인한 범위를 유지하며 다음 인수조건으로 진행한다. 구조를 바꾸는 별도 리팩토링은 기존 품의 규칙을 따른다.

이 방식은 TDD, 즉 테스트를 먼저 써서 실패를 확인한 뒤 구현하는 방식이다. 바이너리 에셋, 자동 생성물, 직접 테스트하기 어려운 플랫폼 연동 등에서 적용할 수 없는 부분은 설계 때 이유와 대체 검증을 명시한다. 이를 전체 테스트 면제나 UI 실제 실행 면제로 해석하지 않는다.

## 5. UI 앱의 Editor 검수 3회

### 개발 실행 환경의 정의

- Godot·Unity 게임: 에디터의 Play/Run으로 실제 게임을 실행한다.
- 웹: 개발 서버와 실제 브라우저에서 UI를 조작한다.
- 네이티브 앱: 개발용 실행과 에뮬레이터 또는 실기기를 사용한다. 개발용 런타임 준비와 배포용 릴리스 빌드를 구분한다.
- UI가 없는 서비스는 대응하는 개발 실행 환경의 API·서비스 E2E를 사용한다.

문서, 코드, 스크린샷만 읽는 것은 실제 실행 검수를 대신하지 못한다. 네이티브 구매·광고·권한 등 개발 실행 환경이 지원하지 않는 기능은 해당 플랫폼의 실기기 증거를 별도로 요구한다. 해당 기능의 검증 부재를 Editor E2E 성공으로 덮지 않는다.

### 공통 회차 절차

각 회차를 시작하기 전에 아래 내용을 작성한다.

- 검수할 후보 SHA와 변경점, 검수 대상 핵심 기능 전체 목록
- 기능 및 UX 관점별 검수 항목·기대 결과·순서
- 검수자 페르소나와 역할, 사용할 실제 실행 환경
- 격리 계정·데이터·저장 경로, 실패·복구 재현 방법
- 통과 기준과 남길 실행 로그·화면·기록

그 뒤 `계획 → 실제 실행 → 검수 판정 → 범위 안의 수정 → 발견 문제 재확인 → 회차 결과 기록`을 수행한다. 검수 계획을 실행 후 소급 작성하지 않는다. 같은 회차 안에서 새 검수 계획을 계속 만들어 3회 상한을 우회하지 않는다. 개발 저장을 초기화하는 테스트는 저장 경로를 먼저 확인하고 사용자 저장과 분리한다.

### 회차별 중심 목표

| 회차 | 기능 검수 | UX 검수 | 검수자 페르소나 |
|---|---|---|---|
| 1회 | 핵심 기능 전체의 인수조건, 상태 전이, 입력·결과·저장 | 화면에서 다음 행동과 결과를 이해할 수 있는가 | 요구사항 검수자 + 처음 사용하는 사용자 |
| 2회 | 핵심 기능 전체 재실행, 오류·취소·연속 입력·복구 | 탐색·피드백·작은 화면·큰 글자·키보드·접근성·터치 | 사용자 관점 검수자, 필요 시 UX 전문가 |
| 3회 | 핵심 기능 전체와 기존 기능의 연결, 회귀, 재시작·저장 복구, 실제 지원 환경 | 작업을 처음부터 끝까지 자연스럽게 완료할 수 있는가 | 회귀·복구 검수자 + 반복 사용자 |

매 회차 기능과 UX를 모두 검수하고 위 표는 각 회차의 집중점을 바꾼다. 1회에서 문제를 발견하지 않아도 2·3회를 수행한다.

검수자의 보고 형식은 `검수 항목 → 실제 관찰·증거 → 기능 또는 UX 문제 → 사용자 영향 → 수정 제안 → 판정`이다. UX 전문가 역할은 새 탐색 구조, 복잡한 입력·상태, 이해하기 어려운 안내, 접근성 문제가 있거나 일반 검수자의 판단이 엇갈릴 때 추가한다. 전문가 검토도 별도 회차를 무제한 추가하는 근거가 되지 않는다.

검수는 구현자와 다른 리뷰 에이전트가 실제 실행 근거를 읽고 재현한다. 작성자가 동일한 역할을 바꿔 읽은 결과를 독립 검수로 세지 않는다. 독립 검수자는 코드·데이터를 임의로 수정하지 않고, 공유 기기·실행 환경은 구현자와 순서를 조율해 사용한다. 페르소나 검수는 실제 사용자 조사와도 구분한다.

### 종료와 추가 회차

3회가 끝나고 전체 인수조건을 충족하며 핵심 기능·사용 흐름을 막는 문제가 없으면 검수 완료로 기록한다. 남은 경미한 지적은 범위와 영향을 보고한다.

3회 후에도 미충족 조건, 주요 기능·UX 결함, 검증하지 못한 항목이 남으면 사람에게 추가 진행을 품의한다. 품의에는 남은 문제·실행 근거, 필요한 추가 회차와 검수 범위, 예상 시간·비용, 추가 검수자 또는 환경, 중단할 때의 영향을 담는다. 승인 전에 4회차를 시작하거나 미검수 상태로 완료 처리하지 않는다.

## 6. 빌드·배포 전 최종 E2E

이번 변경과 지금까지 구현한 기능 전체의 목록을 설계와 함께 관리한다. 각 기능을 하나 이상의 최종 E2E 시나리오에 연결해 누락 여부를 확인하고, 주요 사용자 작업은 기능들을 이어서 실행한다. 최종 후보에서 시작→기능 사용→저장·전환→오류·복구→종료·재실행까지 연결된 시나리오를 수행한다. 단위 테스트와 화면 캡처만으로 이를 대체하지 않는다.

- 배포용 빌드 시작 직전에 개발 실행 환경에서 최종 E2E를 실행한다.
- 이미 만든 산출물을 배포하기 직전에도 현재 환경에서 E2E를 실행하고, 배포 대상 산출물의 소스·설정과 대조한다.
- 최종 소스 SHA, 설정·의존성 식별 정보, 격리 데이터, 실행 환경, 시나리오별 결과와 증거를 남긴다. 비밀값은 기록하지 않는다.
- E2E 이후 코드·에셋·설정·의존성 등 동작에 영향을 주는 입력이 바뀌면 결과를 무효화하고 다시 실행한다.
- 실행 환경이 없거나 일부 필수 시나리오가 차단됐으면 빌드·배포 전 확인을 통과한 것으로 표현하지 않고 해당 단계에서 멈춘다.
- 3회 기능·UX 검수와 최종 E2E는 별도 요구사항이다. 최종 E2E에서 새 기능·UX 결함으로 추가 검수 회차가 필요해지면 위 추가 회차 품의 절차를 따른다.
- Editor E2E 뒤에도 서명 산출물 검사, 마켓별 실기기 QA, 문구 검수, 심사·공개·live 확인은 각각 수행한다.

여기서 말하는 E2E는 사용자의 작업을 시작부터 완료까지 실제 실행해 확인하는 테스트다. 개발 실행 환경의 통과가 배포 산출물이나 마켓 연동을 자동으로 증명하지 않는다.

## 7. 설계 정본·Wiki·티켓 연결

사용자 선택에 따라 레포 `docs/design`을 설계 본문의 정본으로 두고 Wiki에 설계 목록·요약·순서·승인 버전·구현 티켓·PR을 모은다. Obsidian은 조직 간 기획과 검토 대화·승인 결정·회고를 연결한다.

```text
docs/design/YYYY-MM-DD-short-name/design.md
docs/design/YYYY-MM-DD-short-name/visuals/
docs/qa/YYYY-MM-DD-short-name/iteration-1.md
docs/qa/YYYY-MM-DD-short-name/iteration-2.md
docs/qa/YYYY-MM-DD-short-name/iteration-3.md
docs/qa/YYYY-MM-DD-short-name/e2e-before-build.md
docs/qa/YYYY-MM-DD-short-name/e2e-before-deploy.md
```

검수 로그·대용량 영상은 레포 정책에 맞는 로컬 또는 CI 산출물로 보존하고, 보고서에는 위치·해시·환경과 결과를 연결한다. 산출물 보존 기간이 끝나 사라진 링크를 증거가 남아 있는 것처럼 표시하지 않는다.

Wiki의 목록은 설계 날짜·승인 시각 순으로 쌓고, 각 항목에 설계 식별자·현재 상태·최신 원본·승인 커밋·관련 이슈·PR·검수 결과를 표시한다. 승인 버전은 커밋에 고정하고 최신 원본 링크는 별도로 둔다. 대체 설계는 이전 설계와 연결해 기록을 보존한다. 설계 본문을 Wiki와 Obsidian에 각각 복사해 별도 수정하지 않는다.

승인 후 레포별 실행 티켓을 발행하며 하나의 설계가 여러 레포에 걸치면 레포별 범위·인수조건·의존 순서와 공통 설계 링크를 분리한다. 티켓에는 고객 문제, 범위·인수조건, 승인 설계, 테스트 계획, 3회 검수 계획, E2E 시나리오, 실행 환경, 완료 근거와 승인 필요 사항을 포함한다. 모든 티켓·PR·검수 기록에 같은 설계 식별자를 사용한다.

Wiki를 사용할 수 없으면 `docs/design`의 목록으로 같은 순서·연결을 제공한다. 이 경우 Wiki 게시 완료로 표시하지 않는다. Wiki 활성화, 최초 페이지 생성과 외부 게시 대상은 해당 레포의 설정·권한·공개 범위를 확인하고 승인받은 범위에서 진행한다.

[GitHub 공식 문서](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages)는 Wiki가 `.wiki.git` 저장소이며 최초 페이지 생성 후 로컬 clone·push가 가능하다고 설명한다. 이 때문에 코드와 같은 PR에서 설계를 검토하려면 `docs/design`을 정본으로 두는 것이 유리하다는 판단이다. [Wiki는 Mermaid 렌더링을 지원](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)하므로 Markdown 원본 그림을 사용할 수 있다. 독립 공유용 시각 산출물은 기존 `diagram-design`을 적용한다.

Wiki 기능·열람 범위는 [GitHub 요금제와 저장소 공개 상태](https://docs.github.com/en/communities/documenting-your-project-with-wikis/about-wikis)에 따른다. 이번 조회에서 `magicsih/agent-config`는 private·Wiki 비활성, `seorilabs/.github`는 public·Wiki 활성으로 확인했다. 각 앱 레포의 Wiki 상태는 별도로 확인해야 한다.

## 8. 자율 이슈 처리와의 연결

근거 기반 이슈 등록은 계속할 수 있다. 단, 구현을 자동으로 시작할 수 있는 조건에 승인 설계·인수조건·테스트 계획을 추가한다. 설계가 없으면 에이전트는 설계 초안을 작성해 사람 검토를 요청하고 코드를 작성하지 않는다. 승인 대기 항목은 해당 항목의 차단으로 기록하고 다른 적격 작업으로 넘어간다.

사람이 승인한 설계와 범위에 대해서는 구현·3회 검수·PR·CI·병합을 계속 수행한다. 기존 우선순위, 점유, 격리 worktree, 동시 처리 수 1개 규칙은 유지한다. 설계 승인 없이 구현 단계까지 자동 진행하던 예약 흐름은 이 개정 후 승인 대기 단계에서 멈출 수 있다. 승인된 작업만 구현 큐로 들어가므로 예상 작업량과 사람 검토 부담을 `/plan`에서 함께 보여준다.

## 10. 이 설계안의 인수조건

- `/plan`에는 전체 작업의 목록·순서·영향·미확정 사항을 포함하고 구현 승인으로 해석하지 않는다.
- 설계의 9개 필수 요소를 확인하고 사람의 승인 버전이 정해지기 전 구현하지 않는다.
- 설계 원본·승인 버전·Wiki 목록·티켓·PR·검수 결과를 왕복해서 찾을 수 있다.
- 가능한 부분은 요구사항에 해당하는 실패 테스트를 먼저 실행한 뒤 구현하고 통과 증거를 남긴다.
- UI 앱은 매 회차 계획을 작성하고 핵심 기능을 기능·UX 양쪽에서 실제 실행해 3회 검수한다.
- 3회 뒤 미완료 상태에서 승인 없이 추가 회차나 출시 준비를 진행하지 않는다.
- 빌드 전과 배포 전 E2E가 이번 변경과 기존 구현 기능 전체를 포함하며 정확한 후보·설정과 일치한다.
- 정책·템플릿 검증 통과와 실제 제품에서의 3회 검수/E2E 실행은 서로 다른 완료 상태로 보고한다.

## 확정한 선택과 적용 범위

1. 문서 정본은 `docs/design`, Wiki는 순서별 설계 목록·요약·티켓 링크로 확정했다.
2. 검수는 작성자와 다른 리뷰 에이전트가 담당하고 필요한 경우 UX 전문 역할을 추가하는 것으로 확정했다.
3. 사람이 v1을 승인했다. 중앙 정책은 조직 공통으로 적용하며, 이번 변경은 제품 UI나 기능을 변경하지 않는다. 제품별 실제 3회 검수는 다음 승인 구현 티켓에서 수행하고 결과를 별도로 보고한다.
